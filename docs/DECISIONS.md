# Decisions & Assumptions Log (ADR Registry)

## 1. Purpose

The source Project Statement left many implementation details unspecified or marked "optional." Rather than let an AI coding agent or engineer guess silently and inconsistently at the point of implementation, every such gap was resolved here **once**, up front, and referenced by ID (`A-n`) from the document where it applies. This is the authoritative list. If an assumption needs to change, update it here first, then propagate to the referencing document(s) in the same change.

## 3. Architecture Decision Records

### ADR-001: Microservice Boundaries Follow Domain, Not Layer

**Decision:** Services are split by business domain (Auth, News, Category, Search, Scheduler, Admin), not by technical layer (e.g., not a single "API service" + "DB service"). **Rationale:** Matches the source spec's explicit service list and supports independent scaling of the highest-traffic domains (News, Search) separately from low-traffic ones (Auth, Category). **Status:** Accepted.

### ADR-002: Database-per-Service on Shared MySQL Server (A-8)

**Decision:** One MySQL server, one schema per service, logical (not physical) isolation. **Alternatives considered:** One MySQL container per service (rejected: Phase 1 infra overhead not justified at current scale); shared single schema (rejected: violates service independence, `ARCHITECTURE.md` §3.1). **Status:** Accepted. Revisit if a single service's load requires dedicated DB scaling.

### ADR-003: No Message Broker in Phase 1 (A-6)

**Decision:** Scheduler-driven synchronous orchestration with Resilience4j instead of RabbitMQ/Kafka. **Rationale:** The spec marks messaging "optional"; ingestion volume (news APIs, minutes-scale cadence) does not require broker-grade throughput at this phase. Adding a broker prematurely increases operational complexity without a corresponding requirement. **Status:** Accepted. Revisit if ingestion volume/velocity grows (e.g., real-time push ingestion from providers) or if a true event-driven consumer (AI summarization pipeline) is added later.

### ADR-004: Search Service Has No Database (A-9)

**Decision:** Search Service queries News Service's internal endpoint rather than owning a replicated or Elasticsearch-backed copy of article data. **Rationale:** Avoids data-sync complexity in Phase 1 while still keeping Search as an independently deployable, independently scalable service responsible for query/caching concerns. **Status:** Accepted. Documented migration path to Elasticsearch exists (`ARCHITECTURE.md` §6) but is not built now.

### ADR-005: React.js for Frontend

**Decision:** React.js chosen over Thymeleaf/Vue, per the source spec's own "Recommended" marking. **Rationale:** SPA + REST API pairing is consistent with the microservice/API-first architecture; component reusability suits a category/search/article-heavy UI. **Status:** Accepted.

### ADR-006: Docker Compose, Not Kubernetes, for Phase 1 (A-10)

**Decision:** Single-host Docker Compose orchestration. **Rationale:** Matches source spec's explicit Docker/Docker Compose technology stack listing; Kubernetes was not mentioned and introduces significant operational overhead not justified at this phase. **Status:** Accepted. Architecture deliberately avoids decisions that would block a future Kubernetes migration (stateless services, externalized config).

### ADR-007: Regional RSS News Provider and Rome Dependency

**Decision:** Add an `RssNewsProvider` implementing the existing `NewsProvider` Strategy interface to support fetching regional outlet coverage (e.g., Dawn, Express Tribune, ARY News) via their RSS feeds, and add the `com.rometools:rome` dependency for RSS/Atom parsing. **Rationale:** Expanding coverage to regional outlets is not explicitly out-of-scope, and the Strategy pattern naturally accommodates new providers. Using a standard Apache-2.0 library (`rome`) for parsing avoids the complexity and bugs of hand-rolling XML parsing. This provider will be used strictly for search/verification, not scheduled category ingestion. **Status:** Proposed.
